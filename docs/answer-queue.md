# Очередь ответов и фоновое выполнение

Реализация: [AnswerQueue](../src/study_rag/application/answer_queue.py), [ConversationService](../src/study_rag/application/conversations.py), [репозиторий](../src/study_rag/adapters/repositories/conversations.py), [GUI](../frontend/src/Workspace.tsx)

## Приём и выполнение

GUI вызывает `POST /rest/study-rag/answer-jobs/`. После сохранения queued turn и user message возвращается 202 с turn/chat/project ID и статусом. Это подтверждение приёма, а не готового ответа

Серверный worker опрашивает очередь с интервалом 0.5 с. SQL advisory transaction lock `741935` сериализует claim; существующий pending turn занимает единственный слот. Следующий queued выбирается по queued_at, затем UUID. Очередь общая для всех аккаунтов и проектов сервиса, данные чужих задач клиенту не возвращаются

Один worker последовательно выполняет весь поиск, планирование, обзор/генерацию и внутренние повторы одного ответа. Worker индексации независим; embeddings для документа могут выполняться параллельно с ответом

## Состояния и идентификаторы

| Статус | Значение |
| --- | --- |
| queued | Сохранён, ожидает слот, lease отсутствует |
| pending | Выполняется с lease |
| completed | Ответ и citations сохранены |
| failed | Выполнение завершилось ошибкой или остановкой, причина сохраняется |

`client_request_identifier` уникален в рамках чата. Повтор того же UUID и нормализованного вопроса возвращает существующий queued/pending turn либо сохранённый completed результат. Другой текст под тем же UUID даёт 409 request_question_mismatch. Другой запрос в занятом чате даёт 409 chat_busy

Повтор failed запроса через API с прежним UUID возвращает его в очередь без второго user message и обновляет queued_at. Это новая попытка; completed replay не запускает модель повторно и не пересчитывает время ответа. Новый обычный вопрос использует новый UUID

## Наблюдение в браузере

GUI опрашивает `GET /answer-jobs/` примерно через секунду после завершения предыдущего опроса. Список содержит только queued/pending текущего аккаунта во всех проектах. История открытого активного чата перечитывается через REST, завершение также обновляет список чатов

Смена чата, проекта, reload, закрытие вкладки и выход прекращают только локальное наблюдение. Уже принятая задача продолжает работу, пока работает сервер. Отмена/ошибка отправки до получения 202 не доказывает, что задача отсутствует: клиент восстанавливает состояние через историю и прежний request UUID

Статус виден рядом с чатом текущего проекта. Чтобы остановить задачу другого проекта, переключитесь в него и откройте нужный чат. Номер позиции и прогноз времени ожидания интерфейс не показывает

## Остановка и удаление

`POST /answer-jobs/{turn_identifier}/stop/` возвращает 204. queued/pending меняется на failed с answer_stopped, lease отзывается. Worker замечает изменение через свой опрос, отменяет локальную задачу/ожидание model HTTP и освобождает очередь

Если completed commit уже победил в гонке, сохранённый ответ остаётся. Повтор stop безопасен для существующего turn. Остановка Python HTTP-ожидания не обещает мгновенного прекращения внутренних GPU-вычислений Ollama

Удаление чата/проекта физически удаляет его turns/messages и помечает пространство недоступным. Worker прекращает работу после проверки, поздняя запись не допускается. Удаление документа само по себе не является командой остановки ответа

## Время и перезапуск

Общий бюджет обработки - 240 с, lease - 300 с. Настройки требуют `answer_timeout_seconds + 10 < turn_lease_seconds`. Для ответов heartbeat не реализован: работа ограничена бюджетом меньше срока lease

Ожидание queued не расходует бюджет ответа. `response_duration_ms` включает получение истории, поиск, вызовы моделей и повторы до сохранения; исключает очередь, финальный commit и доставку по сети. Старые assistant messages могут иметь null, user messages имеют null

При штатном shutdown выполняемый ответ отменяется с answer_cancelled, queued остаются. После аварии pending **не возобновляется с середины и не перезапускается автоматически**: после истечения lease следующий claim помечает его failed с turn_lease_expired, затем очередь продолжает работу. Пользователь может повторить failed запрос

Ошибки одного ответа не должны удерживать pending-слот. Инфраструктурная ошибка очереди фиксируется в логах. Health возвращает unavailable, если задача answer worker завершилась

## Совместимые транспорты

`POST /messages/` ждёт результат этой же очереди и возвращает AnswerResponse. `POST /rpc/study-rag/agent/` через официальный AGUIAdapter/FunctionModel ждёт тот же результат и передаёт SSE lifecycle/готовый текст

Разрыв ожидания не отменяет принятую задачу. Это не поток отдельных токенов Ollama. Источники и постоянные ID читаются из REST history
